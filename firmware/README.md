# nano24 firmware status and flashing

**Only the hardware configuration JSON is included. No firmware binary, complete flash image, validated build or registered nano24 device target is available yet.**

## Build family and hardware map

The intended ExpressLRS environment is `Unified_ESP32C3_2400_RX_via_UART`, with `receiver-hardware.json` incorporated using the chosen ELRS release's target/configuration mechanism. This is an ESP32-C3 + SX1281 board. Do not use an ESP8285 / RadioMaster RP1 firmware image.

| Signal | ESP32-C3 GPIO |
| --- | --- |
| Receiver UART RX, TP1 | 20 |
| Receiver UART TX, TP2 | 21 |
| Radio SPI MISO | 5 |
| Radio SPI MOSI | 4 |
| Radio SPI clock | 6 |
| Radio chip select / NSS | 7 |
| Radio reset | 2 |
| Radio busy | 3 |
| Radio DIO1 | 1 |
| RGB LED data | 8, GRB order |
| BOOT pad TP5 | 9; currently not assigned as a runtime firmware button |

The JSON's single RF output-power setting is an initial reference configuration, not a calibrated output-power measurement. Verify telemetry output on assembled hardware.

## Work required before issuing an image

1. Select and record a supported ELRS release compatible with the intended transmitter.
2. Define a nano24 target/layout using the exact pin map and applicable power settings.
3. Produce the full UART flash artifacts, including the MCU bootloader and partition information. An OTA application file alone is not a complete first-flash package for a blank chip.
4. Record the build environment, source revision, options, regulatory-domain selection, artifact checksums and exact flash command generated by that build.
5. Verify boot, radio initialization, LED behavior, UART/CRSF, binding, telemetry and recovery on a prototype.

No fixed flash offsets or ready-to-use flashing command are supplied until that version-specific package has been built and checked. Do not treat this JSON as something that can itself be flashed to a blank chip.

## Physical first-flash connection

Use a USB-to-UART adapter with **3.3 V signal levels**. Connect adapter TXD to receiver RX, adapter RXD to receiver TX, and adapter GND to receiver minus. Power the receiver's plus pad from **regulated 5 V**, with a common ground. Disconnect the FC while using a separate UART adapter. Fit the main ELRS antenna before powering the radio.

Connect **B/TP5 to GND before applying power**. GPIO9 low at reset selects the ESP32-C3 ROM download mode. The circuit includes the GPIO8 pull-up needed for its download strapping condition; this remains subject to physical verification. Flash using the completed build's instructions, remove the B-to-GND connection and power-cycle afterward. There is no wired DTR/RTS automatic-reset interface on these pads.

Reference: [Espressif ESP32-C3 boot-mode selection](https://docs.espressif.com/projects/esptool/en/latest/esp32c3/advanced-topics/boot-mode-selection.html).

## Binding and updates

The intended firmware supports binding phrases, FC-requested binding, initial unbound startup and the standard three-power-cycle procedure. FC-requested UART binding requires compatible versions; support was introduced in ELRS 3.4.0, Betaflight 4.5.0 and Configurator 10.10. Use `bind_rx` or the Receiver-tab button, then Bind on the transmitter.

A genuinely unbound receiver has no saved binding or preset phrase. A bound receiver that cannot currently hear its transmitter should keep its stored identity. Automatic Wi-Fi startup is a separate timeout, not automatic deletion of the binding.

The current JSON does not configure B/TP5 as a runtime bind button. Shorting it during startup is for ROM download mode. A runtime button action would require an explicit firmware configuration and verification.

UART, Betaflight passthrough and Wi-Fi update paths are planned. Wi-Fi also depends on successful antenna tuning. No update path has been tested on a physical nano24 board.
